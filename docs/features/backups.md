# Backups

Backup policy configuration, scheduled/manual backup queueing, agent execution,
artifact recording, retention cleanup, and artifact-level restore are
implemented.

The UI and mutation/scheduler endpoints are disabled unless
`DEVPUSH_BACKUPS_ENABLED=true`. Local Vite development also requires
`VITE_DEVPUSH_BACKUPS_ENABLED=true` so the client renders the Backups UI; the
production image derives that build flag from `DEVPUSH_BACKUPS_ENABLED`. This
flag is separate from control-plane PostgreSQL backups described in
[Production operations](../development/production-operations.md).

## Scope

V1 backups cover devpush-managed Docker Compose runtimes for a single
environment on a single server.

Backups can include:

- Compose-scoped named volumes for the environment runtime.
- Optional database dump commands for selected services.
- A manifest with run metadata and artifact checksums.
- Local artifacts on the server.
- Optional remote artifacts in S3-compatible object storage.

Backups do not include:

- Bind mounts outside Docker-managed volume paths.
- Anonymous volumes.
- External managed databases.
- Third-party log or object-store backup policies.

## Scheduling

The control plane owns scheduling. A process should call:

```text
POST /api/cron/backups
Authorization: Bearer <DEVPUSH_CRON_SECRET>
```

once per minute. `DEVPUSH_CRON_SECRET` is required when the feature is enabled.
The cron route enqueues due backup runs for enabled
policies. Cron expressions are evaluated in UTC. Agents only poll and execute
queued jobs; they do not schedule backup runs themselves.

Manual backup runs can also be queued from the Backups page.

## Local artifacts

Each backup run writes artifacts under:

```text
/var/lib/devpush/backups/<projectId>/<environmentId>/<policyId>/<runId>/
```

The run directory contains:

- `manifest.json`: backup run ID, runtime ID, timestamps, and future metadata.
- `volumes/<volume>.tar.gz`: archived named Compose volume contents.
- `databases/<index>-<service>.sql.gz`: stdout from a configured dump command.

Artifact names are generated by devpush. Users configure what to back up, not
the object/file names.

## Remote backups

Remote backups are optional per policy. When enabled, the agent uploads the
local artifacts to S3-compatible storage with `rclone` using a temporary 0600
config file. S3 credentials are stored encrypted by the control plane and are
sent to the agent only in the backup or cleanup job payload.

Remote object keys are deterministic:

```text
projects/<projectId>/environments/<environmentId>/backups/<policyId>/<runId>/<artifact>
```

Servers need `rclone` installed for remote backups. The installer attempts to
install it on apt-based hosts and warns when it cannot.

## Retention

Retention is configured separately for local and remote artifacts:

- Count: keep at least the newest N successful runs.
- Days: delete successful runs older than N days.
- Max storage: keep newest successful runs until artifact bytes exceed the GB
  cap, then queue cleanup for older runs.

The control plane decides what is expired from recorded
`backup_artifacts.size_bytes` and queues `backup_cleanup` jobs. The agent deletes
local files and remote S3 objects. Cleanup failure does not make the original
backup run fail.

## Database dumps

Database dumps are explicit commands run inside the target Compose runtime:

```sh
docker compose -p <runtimeId> exec -T <service> sh -lc '<command>'
```

The agent captures stdout to a gzip-compressed `.sql.gz` file. Dump commands
should write the dump to stdout. Secrets needed by the command should come from
the running service environment.

If no database dump is configured, volume backups of live databases are only
crash-consistent.

## Volume archives

Volume backups cover named Compose volumes discovered from Docker labels:

```text
com.docker.compose.project=<runtimeId>
```

The agent uses an ephemeral helper container with the source volume mounted
read-only and creates a gzip tar archive. Containers are not stopped during
backup; volume archives are crash-consistent.

## Restore

V1 restore creates an explicit `restore` agent job from selected backup
artifacts. The backend payload accepts multiple artifacts so volume and database
restores can be grouped later. The first UI exposes restore from individual
artifact rows on successful backup runs.

Supported now:

- Restore volume artifacts into a selected target Compose volume.
- Restore database dump artifacts into a selected target service with a restore
  command.
- Download remote artifacts through `rclone` when the selected artifact is in
  remote storage.
- Verify artifact SHA-256 before applying it.

Volume restore stops containers in the target runtime, clears the target volume,
extracts the archived files, then starts the containers again. Database restore
streams the decompressed dump to the configured command over stdin with:

```sh
docker compose -p <runtimeId> exec -T <service> sh -lc '<restoreCommand>'
```
