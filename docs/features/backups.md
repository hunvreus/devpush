# Backups

Backup policy configuration, scheduled/manual backup queueing, agent execution,
artifact recording, retention cleanup, and artifact-level restore are
implemented.

The UI and mutation/scheduler endpoints are disabled unless
`DEVPUSH_BACKUPS_ENABLED=true`. Local Vite development also requires
`VITE_DEVPUSH_BACKUPS_ENABLED=true` so the client renders the Backups UI; the
production image derives that build flag from `DEVPUSH_BACKUPS_ENABLED`. This
flag is separate from control-plane PostgreSQL backups described in
[Production operations](../development/production-operations.md).

Team owners and admins may configure policies, run backups and restore data.
Members may view policies, runs and restore results, but cannot start jobs or
manage storage.

## Scope

V1 backups cover devpush-managed Docker Compose runtimes for a single
environment on a single server.

Backups can include:

- Compose-scoped named volumes for the environment runtime.
- Database backups for PostgreSQL, MySQL, MariaDB and MongoDB Compose services.
- A manifest with run metadata and artifact checksums.
- Local artifacts on the server.
- Optional remote artifacts in S3-compatible object storage.

Backups do not include:

- Bind mounts outside Docker-managed volume paths.
- Anonymous volumes.
- External managed databases.
- Third-party log or object-store backup policies.

## Scheduling

The control plane owns scheduling. A process should call:

```text
POST /api/cron/backups
Authorization: Bearer <DEVPUSH_CRON_SECRET>
```

once per minute. `DEVPUSH_CRON_SECRET` is required when the feature is enabled.
The cron route enqueues due backup runs for enabled
policies. Cron expressions are evaluated in UTC. Agents only poll and execute
queued jobs; they do not schedule backup runs themselves.

Cron uses standard five-field semantics, including OR behavior when both day of
month and day of week are constrained. A schedule-minute key prevents duplicate
enqueues, and the database permits only one queued or running backup per
environment.

Manual backup runs can also be queued from the Backups page.

## Local artifacts

Each backup run writes artifacts under:

```text
/var/lib/devpush-agent/backups/<projectId>/<environmentId>/<runId>/
```

The run directory contains:

- `manifest.json`: backup run ID, runtime ID, timestamps, and future metadata.
- `volumes/<volume>.tar.gz`: archived named Compose volume contents.
- `databases/<index>-<service>.sql.gz`: stdout from a configured dump command.

Artifact names are generated by devpush. Users configure what to back up, not
the object/file names.

Manual backups start from the chosen policy’s **Run** action. The Runs section
shows history and does not implicitly select a policy.

## Remote backups

Remote backups are optional per policy. When enabled, the agent uploads the
local artifacts to S3-compatible storage with `rclone` using a temporary 0600
config file. S3 credentials are stored encrypted by the control plane. Queued
jobs retain only ciphertext; the secret is decrypted and returned only when an
authenticated compatible agent claims a backup, restore, or cleanup job.

Workspace owners and admins add reusable destinations in **Settings → Backup
storage**. A workspace can have multiple destinations; each project policy
selects one destination. Devpush automatically assigns a folder path in the
bucket; existing configured paths are preserved without an editable field.
A project can therefore use
different destinations across policies. One policy uploads to one remote
destination; it does not mirror files to multiple buckets.

Create the bucket with the provider first. Each connection has a name, bucket,
region, optional S3-compatible endpoint, access key ID and secret. Members can
read destination metadata but cannot add/edit storage or read credentials. Names
and credentials can be updated; bucket, region and endpoint are immutable. Add
another destination and select it in the policy to change location. Leaving a
replacement secret empty keeps the saved encrypted secret.

Each queued run records its policy ID and original destination snapshot. Restore
and retention use that original bucket/endpoint, with the saved connection’s
current credentials, regardless of later policy changes or deletion. Owners and admins may remove unused storage connections after confirmation.
Removal never deletes the bucket or its files; policies, active backups and
retained remote artifacts block removal. Database guards protect references
against concurrent writes. Legacy connections and retained backup-job
locations are migrated into workspace destinations; older remote runs whose
original destination cannot be recovered fail restoration explicitly rather
than using a policy’s current bucket.

If a remote upload fails after the local archive is complete, the run remains
**Failed** and its local files remain available for restoration. The run and
policy show a storage failure alert; local recovery appears only while retained
local volume/database artifacts exist. A successful subsequent run clears the
policy failure alert. Local retention also applies to these failed-upload
archives. No upload failure silently becomes a successful local-only backup.
Failures while building an archive still remove incomplete output.

Storage settings validate input syntax but do not currently test provider access.
Live S3 validation and a deployment-server connection test remain in TODO.

Remote object keys are deterministic:

```text
projects/<projectId>/environments/<environmentId>/backups/<policyId>/<runId>/<artifact>
```

Servers need `rclone` installed for remote backups. The installer attempts to
install it through apt, dnf, or yum when available and warns when it cannot.

## Retention

Retention is configured separately for local and remote artifacts:

- Count: keep the newest N runs with retained files in that storage location.
- Days: delete retained files from runs older than N days.
- Max storage: keep newest runs with files until artifact bytes exceed the GB
  cap, then queue cleanup for older runs.

The control plane decides what is expired from recorded
`backup_artifacts.size_bytes` and queues `backup_cleanup` jobs. The agent deletes
local files and remote S3 objects. Cleanup failure does not make the original
backup run fail. A failed remote upload with a usable local archive participates
in local retention only; it does not displace the last successful remote copy.

## Database backups

Select a Compose service, database engine and database name. An empty name backs
up all databases. The control plane generates engine-specific backup and restore
commands; users do not supply shell commands. Credentials come from standard
container environment variables: `POSTGRES_USER` / `POSTGRES_PASSWORD`,
`MYSQL_ROOT_PASSWORD`, `MARIADB_ROOT_PASSWORD` (falling back to
`MYSQL_ROOT_PASSWORD`), or `MONGO_INITDB_ROOT_USERNAME` /
`MONGO_INITDB_ROOT_PASSWORD`. Custom images must provide those variables and the
engine's client tools.

PostgreSQL creates plain SQL, MySQL/MariaDB create SQL dumps, and MongoDB creates
an archive. The agent captures stdout and compresses it once. MongoDB uses
`.archive.gz`; SQL engines use `.sql.gz`. Restore uses engine and scope saved
with the original run, even after its policy is edited or deleted. It imports
into the selected service; stop application writes before restoring. PostgreSQL
all-database backups concatenate individual database dumps and restore through
`template1`, avoiding duplicate role creation. They recreate the backed-up
databases and omit role ownership, grants, and cluster-wide settings. Provision
required roles separately and validate recovery on a disposable database.

Migration `0006_backup_database_engines` converts known preset commands. Other
commands are preserved as `legacyCommand`, marked `needs_configuration`, and
the policy is paused. Select a supported engine and scope before re-enabling it.
Historical artifacts with unknown engine metadata require manual recovery;
files are retained. MongoDB requires an agent advertising `jobs.backup.archive.v1`.

Volume archives of a live database are not guaranteed to be consistent. Use
engine-native backups for running databases.

## Volume archives

Volume backups cover named Compose volumes discovered from Docker labels:

```text
com.docker.compose.project=<runtimeId>
```

Selected backup volumes and restore targets must carry that same runtime label.
The agent rejects volumes belonging to another Compose project or unrelated
Docker workloads before mounting them.

The agent uses an ephemeral helper container with the source volume mounted
read-only and creates a gzip tar archive. Containers are not stopped during
backup. Files may change while tar reads them, so the archive is not an atomic
snapshot and may contain inconsistent application or database state. Use a
database-native dump command for databases. A stopped-writer backup mode is not
yet implemented.

## Restore

V1 restore creates an explicit `restore` agent job from selected backup
artifacts. The backend payload accepts multiple artifacts so volume and database
restores can be grouped later. The UI exposes a direct Restore button on successful backup runs. If multiple
restorable files exist, the dialog selects one file at a time, including its
local or remote copy. Fixed backup details are shown as text. Volume targets use
Compose names rather than generated runtime prefixes; the agent resolves and
checks ownership before restoring.

Supported now:

- Restore volume artifacts into a selected target Compose volume.
- Restore supported database artifacts into a selected target service using a generated command.
- Download remote artifacts through `rclone` when the selected artifact is in
  remote storage.
- Verify artifact SHA-256 before applying it.

Volume restore stops containers in the target runtime, clears the target volume,
extracts the archived files, then starts the containers again. Database restore
streams the decompressed dump to the generated engine command over stdin with:

```sh
docker compose -p <runtimeId> exec -T <service> sh -lc '<restoreCommand>'
```

## Backup page

Policies support Run, Pause (or Resume when paused), and Delete. Deleting a
policy removes its configuration, not the existing stored files. Runs show artifact counts and restore availability. File sizes are shown in
the restore dialog, alongside the filename, creation time, storage location and
a filename action that copies the full server path or S3 object key (also
available on hover). Source and Target are stacked vertically with a downward
arrow. A dialog-wide alert below both blocks explains the restoration risks. The target shows its environment, current server and
Compose volume/service. Restore is the only run action. Download is under
consideration; manual deletion of backup files is intentionally not offered.

The latest restore attempt appears in the **Latest restore** column as queued,
running, succeeded or failed. Its timestamp is available on hover or keyboard
focus; completed restores do not add another line to the run. Failures use a concise alert with expandable
error details. Restore controls are disabled while another restore is queued or
running for that environment. Workspace events refresh results; HTTP fallback
polls every two seconds while backup or restore jobs are active, and every 15
seconds while idle. Only status metadata is sent to viewers, never job payloads
or storage credentials.

## Validation

On October 9, 2026, the local control plane and Hetzner test agent passed:

- Local and R2 volume recovery, with a marker checksum verified and the local
  archive moved aside during remote recovery.
- PostgreSQL 17 `pg_dump --clean --if-exists` backup and `psql` recovery from R2
  and local gzip artifacts. A changed row recovered its original value.
- Authenticated cron enqueueing and duplicate suppression for the same minute,
  followed by agent execution.
- Count retention deleting older local files and R2 objects while preserving run
  history; failed uploads preserve the most recent successful remote copy.
- Invalid remote credentials, retained local recovery, deliberate restore-command
  failure, and live terminal result updates.

Integration tests cover member mutation restrictions, workspace scoping, safe
restore metadata, schedule concurrency, and age/size retention. The deployment's
automatic Cloudflare cron trigger still needs a staging check; invoking the local
cron endpoint does not validate that infrastructure.

## Backup targets

Policies use one Backup targets list. Each entry is a named Compose volume or a
Database backup with a Compose service, engine and database scope. All named
volumes remains available as an aggregate selection. Targets share the policy
schedule, storage and retention settings. Backup summaries count archives and
dumps once, excluding metadata manifests and duplicate remote copies.

Legacy PostgreSQL cluster dumps retain their files but require manual restoration: migration `0007_legacy_postgres_restore` marks those historical artifacts accordingly. Converted policies produce the new generated format on their next run.
